# 任务状态查询

## 何时使用

命中以下任意一种说法就调用本技能：

- 「任务跑完了吗？」
- 「刚才提交的那个好了吗？」
- 「job 状态 / job 状态怎么样」
- 「还要多久？」
- 「昨天的因子挖掘跑完了没？」
- 「刚才批量预测那批出结果了吗？」

**不适用**：用户想**新**跑一个任务 → 那是提交环节（先拿 job_id），本技能只负责查已经提交过的任务。用户查的是**同步**工具的结果（如 `mcp__factor-miner__factor_execute`、`mcp__kronos__forecast_signal`）→ 那些当场就返回，没有 job_id，不走本技能。

## 轻问 vs 深问（成本控制）

**轻问（1 个工具，秒级返回，优先默认走这条）**
- 根据任务所属命名空间调一次对应的 `*job_status(job_id)`，读出 `status` 直接回答。
- 适用：用户只想知道「好了没 / 还要多久」。回复 2-5 行即可。

**深问（完整链路 + 结构化报告）**
1. 先确认 job_id（用户没给就从对话上文里找那次提交返回的 id）
2. 确认命名空间（见下方「三套命名空间怎么选」表），调对应的 `*job_status(job_id)`
3. `status` 仍在 `queued/running` → 看 `elapsed_sec`，给出「已跑 X 分钟」+ 建议稍后再问
4. `status = done` → 读 `result`，做**摘要**（不要整段贴原始 JSON）：
   - 因子回测类：看 `ok`、`metrics`（IC/年化/最大回撤）、`dedup_dropped`、`sota_broken`、`error`
   - 数据更新类：看 `ok`、`exit_code`、`provider_uri`、`out_dir`
   - Kronos 批量类：逐项 `error` 统计 + 成功项的方向/预期收益；**模型输出，非承诺**
   - 因果批量类：成功/失败事件数 + 显著事件（CAR 方向、p 值）摘要
5. `status = error` → 原文回传 `error` 字段要点，给一句下一步建议（检查输入数据/参数后重提），**不猜原因**
6. 给出「怎么读这份结果」的 2-3 句解读（只讲统计含义）

**哪一步最贵**：
- **没有工具调用本身是重任务** —— `*job_status` 只是一次轻量查询，不消耗算力。**最贵的永远是用户原先提交的那个任务**（尤其 `mcp__factor-miner__factor_backtest` 全量回测和 `mcp__factor-miner__update_data` 数据重建，动辄十几分钟到数小时）。
- 所以本技能的铁律是：**查询只读一次，不要为了「看进度」反复连打**。`running` 时不要短间隔轮询，告知用户 ETA 量级即可。
- 重跑（重新提交任务）是本技能里唯一的高成本动作，**必须用户明确要求才做**。

## 工具链

### 第 0 步：确认命名空间（最容易错的一步）

job_id 是**分命名空间**的，同一个 id 串在另一套工具里查不到。按任务是从哪套工具提交的来选：

| 提交时用的工具族 | 轮询用哪个 |
| --- | --- |
| `mcp__factor-miner__factor_backtest` / `mcp__factor-miner__update_data`（因子回测、数据更新、因子挖掘类重任务） | `mcp__factor-miner__job_status(job_id)` |
| `mcp__causal__event_study_batch`（批量因果事件研究）等 `causal-*` 重任务 | `mcp__causal__job_status(job_id)` |
| `mcp__kronos__forecast_batch`（批量 K 线预测） | `mcp__kronos__job_status(job_id)` |

判不准时：先问用户「这个任务是**因子回测/数据更新**、**因果事件研究**、还是**Kronos 批量预测**？」，或者回看对话上文那次提交的工具名 —— **不要三套连着试**（一套查不到就是查不到，乱试只会让用户困惑）。

### 第 1 步：拿到 job_id

```
job_id = 提交那次工具返回的 job_id
```

- 这些 `*job_status` 工具**只接受 `job_id` 一个参数**，不需要 klines、不需要标的代码，也不需要用户重新提供行情数据（数据来源是提交时那次调用的入参）。
- 用户忘了 job_id：从对话上文里翻出提交返回的 id；翻不到就直说「请把提交时返回的 job_id 再发我一次」，**不要编造 id，也不要凭标的代码猜 id**。

### 第 2 步：查一次状态

```
mcp__factor-miner__job_status(job_id = "<id>")     # 或 mcp__causal__job_status / mcp__kronos__job_status
```

返回字段：

- `status`：`queued`（排队中）/ `running`（执行中）/ `done`（完成）/ `error`（失败）
- `result`：仅 `done` 时有值（`error` 时无 result，改看 `error`）
- `error`：仅 `error` 时有值
- `elapsed_sec`：已耗时（秒）——**判断「还要多久」就靠它**，用已耗时和任务类型做量级估计，不要给精确分钟数承诺

### 第 3 步：状态不是 done/error 时的处理

- `queued`：还没轮到执行。告知「已排队，还没开始跑」，按任务量级给一个「大概还要等一会儿」的说法。
- `running`：告知已跑多久（`elapsed_sec`），然后**停手**，让用户过几分钟再问。
- **不要循环短间隔轮询**（例如每 10 秒打一次），也不要阻塞式死等 —— 这是重任务，进度不会因为查得勤而变快。

### 第 4 步：done / error 的处理

- `done`：展示 `result` **摘要**（关键指标 + 成败标记 + 失败项计数），原始 JSON 只在用户明确要求时给，长结果可落成文件再 present。
- `error`：原文回传 `error` 要点，给下一步排查方向，不编造失败原因。

### 第 5 步：超时/查不到

- **异步任务结果默认只保留 1 小时**。超过 1 小时后 job_id 查不到（或返回未命中）是**正常现象**，如实告诉用户「已超出 1 小时保留窗口，需要重新提交」，**不要伪造一份结果**。
- 重新提交属于重任务，**必须先征得用户同意**，提交后同样回到「拿 job_id → 轮询」流程。

## 记忆回路（前查后记）

| 时机 | 动作 | 工具 |
|---|---|---|
| 执行前 | 查同类任务（因子回测 / 数据更新 / 因果批量 / Kronos 批量）历史上的**实际耗时与 ETA 估算偏差**，用来校准本次「还要多久」的量级说法 | `search_causal`（query=「因子回测/数据更新/Kronos/因果批量 异步任务 耗时 elapsed_sec ETA 量级估计」，task_tag=`task-status`） |
| 执行后 | 写下本次判定：job_id + 命名空间 + 任务类型 + 当时的 `status`/`elapsed_sec` + 给出的 ETA 量级说法 | `record_decision`（decision=`<任务类型> job_id=<id> 查到 status=<queued/running/done/error>，elapsed_sec=<N>，给出 ETA 量级=<说法>`，outcome="待验证"，context=`命名空间/任务类型 + 输入规模（标的数、loops、事件数、klines 长度）`） |
| 复检时 | 用户后续再来问、或该 job 转为 `done`/`error` 时，用**同一条 decision** 回填真实结束情况 | `record_decision`（同一条 decision，outcome=`最终 status + 总耗时 elapsed_sec + （done 时）结果摘要要点；超 1 小时查不到则 outcome="超出保留窗口未取到最终结果"`） |

本技能的历史参照维度是**「同类异步任务的实际耗时」与 ETA 量级估算是否靠谱**：记录的是「某任务类型 + 某输入规模 → 实际跑了多久 / 是否在估算量级内」这条因果边。它对用户的价值在于：`*job_status` 本身只返回 `elapsed_sec` 一个时间信号，工具里**没有任何历史耗时基准**，所以「还要多久」这句回答完全依赖过去的经验沉淀 —— 有了记忆回路，同类任务第二次被问时就能给出有依据的量级区间（例如「这类全量回测历史上跑过 3 次，都在十几分钟量级」），而不是每次从零猜；同时也能识别出**常超时/常报错的任务形态**，在用户再次提交前提示风险。

## 输出格式

Agent 回复必须包含以下小节，字段名可中文化但不得缺项：

1. **任务识别**：job_id、命名空间（因子 / 因果 / Kronos）、任务类型、提交时间（如已知）。
2. **当前状态**：`queued` / `running` / `done` / `error`（中文说明并列原文英文值）。
3. **已耗时**：`elapsed_sec` 换算成「约 X 分 Y 秒」；`queued/running` 时给量级 ETA 说法（如「这类全量回测通常十几分钟量级」），**不给精确完成时间承诺**。
4. **结果摘要**（仅 `done`）：按任务类型列关键字段（见轻问/深问第 4 条），并单列失败项数量与原因要点。
5. **结论一句话**：跑完了/还在跑/失败了，以及建议动作（等一会儿再问 / 重新提交 / 检查输入）。
6. **保留期提示**：提及「异步结果默认保留 1 小时」，尤其当用户隔了很久才来查时。
7. **模型/结果声明**（涉及 Kronos 或 ML 预测结果时，不可省略）：
   > 以上为模型输出的**统计结果，非承诺**，不构成任何投资建议。
8. **历史参照**（必填小节）：
   > **历史参照**（必填小节）：若检索到同类历史，写明「类似情境 N 次，其中 X 次 <本技能的判断维度> 正确」；
   > 无历史则写「首次记录此类情境，本次判断已存入记忆供将来对照」。

## 合规边界

- 只输出**任务状态与统计计算结果**：状态、耗时、IC/年化/最大回撤等指标、成功失败项计数。
- **不输出**：买入/卖出/加仓/减仓建议、目标价、止盈止损价位、仓位比例、收益承诺、胜率承诺。
- Kronos / ML 因子预测类结果一律标注**「模型输出，非承诺」**，不得用「准」「必涨」类措辞。
- 查不到、超时、失败都**如实说明**，绝不伪造 job_id、编造进度百分比或补造结果数值。
- 不替用户决定重提任务；重任务重跑需用户明确同意，并提示成本与耗时。

## 常见问题

1. **「查不到这个 job_id，是不是坏了？」**
   先排三种正常情况：(a) **超过 1 小时保留窗口**（最常见）；(b) **命名空间选错了** —— 用 `mcp__kronos__job_status` 查因子回测的 id 必然查不到；(c) id 复制缺字符。依次排除后如实回答，不要硬猜结果。

2. **「能不能显示进度到 30% 了？」**
   工具只返回 `status` + `elapsed_sec`，**没有百分比字段**。不要编造进度条，用状态 + 已耗时 + 任务类型给量级估计。

3. **「我每隔几秒问一次行不行？」**
   不建议。查询不加速任务，反而干扰判断。建议 `running` 时至少间隔几分钟再问一次；`queued` 时等更久。拿到 `done` 后一次性把结果摘要看完即可。

4. **「任务失败了要不要自动重跑？」**
   不要自动重跑。先回传 `error` 要点，让用户确认输入数据/参数没问题，同意后再重新提交 —— 全量回测和数据重建都是高成本任务。
