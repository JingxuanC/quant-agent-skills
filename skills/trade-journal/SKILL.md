# 交易决策记账

## 何时使用

用户出现下面这类意思时，触发本技能：

1. 「记一下我这次买的」——刚成交或刚下单
2. 「把我这个判断存下来，以后回头看」——只是看法，不一定有交易
3. 「我昨天加仓了 XXX / 我把 XX 卖了」——补记已发生的操作
4. 「记录一下我的操作，理由是我觉得……」——用户自己已经开始说理由了
5. 「我之前是不是也这么想过？」——用户想找旧记录（走检索分支）
6. 「这个月我判断对了几次？」——想复盘命中率（走检索/统计分支）

注意区分：用户只是想**存**（写记忆），还是想**查**（读记忆）。一句话里常常两者都有（先存这次的，再对比上次的）。

## 核心机制

**这是一个「入口」技能，不是分析技能。** 它的全部价值在于：把用户口语化的操作和判断，拆成四要素、写成一条可回溯的记忆边。没有这一步，后面所有复盘、归因、命中率统计都是空的。

四要素（缺一条就主动追问，不要自己编）：

| 要素 | 说明 | 落到哪个字段 |
|---|---|---|
| ① 做了什么 | 买入/卖出/加仓/减仓/清仓/只是观察不操作 | `decision` |
| ② 为什么 | 当时的理由、看到了什么、依据什么 | `context` |
| ③ 预期什么 | 预期涨/跌/横盘、什么信号出现算验证 | `outcome` 先写成「预期：……」 |
| ④ 多久验证 | 3 天 / 1 周 / 1 个月 / 到某个点位 / 到财报日 | `task_tag` 附期限，正文里写清 |

**两条铁律：**

- **首次落账，`relation` 一律填 `no_effect`**。结果还没发生，关系未定。caused / enabled / prevented 是**回填**时才允许出现的词——那时你才知道这笔决策到底引出了什么结果。
- **首次落账，`outcome` 写「预期：……」，不要写成「赚了/亏了」**。把预期先立起来，将来的真实结果才有对照物。等验证期到了或用户说了结果，再用**同一条 decision 文本**再记一次，把真实结果写进 `outcome`，并更新 `relation`。

**什么时候写：** 用户一说操作/判断就写，别攒着。信息不全就先记录已确认的部分，并明确告诉用户「我记了这些，还差 X」。

**什么时候查：** 写新记录之前，先按标的或主题查一次历史（`search_causal`），如果查到了同类旧决策，就提醒用户「你上次也这么判断过，当时的记录是……」——这是这个技能最有用的时刻。用户问「我判断对了几次」时，也走检索 + `prediction_report`。

## 工具链

### A. 写记忆（用户说「记一下……」）

**第 1 步：先查（可选但推荐，留个上下文）**
```
search_causal(query="<标的或其理由的关键词>", task_tag="trade-journal", limit=5)
```
├─ 查到同类旧决策 → 在回复里点一句「上次类似记录：……」；把它写进本次 `context` 的末尾，例如「同标的 3 月曾记录过一次相反判断」。
└─ 没查到 → 直接进第 2 步。

**第 2 步：补齐四要素**（缺哪补哪，用一句人话问，一次问全，别连环追问）
> 「我记下来。再确认两点：一是你当时主要看什么？二是这个判断你想多久回头验证——3 天、一周还是一个月？」

**第 3 步：落账主记录**
```
record_decision(
  decision   = "<标的> <动作>：如「sz300308 加仓 200 股，成本 128.5」或「判断光模块三季度还有一波，暂不操作」",
  outcome    = "预期：<预期什么 + 什么信号算验证>",
  relation   = "no_effect",
  task_tag   = "trade-journal.<标的或主题>.<验证期限>",   # 如 trade-journal.sz300308.1w
  context    = "<用户给出的理由，尽量用他自己的话>；<当时的价格/大盘/事件背景>；<查到的相关历史记录>",
  confidence_source = "user_feedback"
)
```
- 用户没给理由 → `context` 写「用户未说明理由」，不要替他编一个。
- 纯判断无操作 → `decision` 写成判断本身，一样要写验证期限。
- 同时记了多笔 → 一笔一条，别合并成一条。

**第 4 步：沉淀稳定事实（只在真有稳定信息时）**
```
record_fact(key="持仓特征", value="<标的、风格偏好、可承受回撤、验证习惯>", scope="user", confidence=0.8)
```
- 只在用户明确表达的稳定偏好/参数上调用（例如「我一般只做 3 天以内的」「我不用杠杆」）。一次的临时操作不要记成事实。
- 同一件事更新了 → 传 `replace_same_key=true`，避免事实层堆积矛盾。

**第 5 步：回执**（按「输出格式」给用户看，必须带上之后怎么回填）

### B. 回填结果（验证期到了，或用户说「那笔结果怎么样」）

**第 1 步：找出原记录**
```
search_causal(query="<标的> <动作>", task_tag="trade-journal.<标的>.<期限>", limit=5)
```

**第 2 步：核对事实来源**——收益/价格以用户提供的成交与行情为准，不猜。用户没给结果就只问、不写。

**第 3 步：用同一条 decision 再记一次**
```
record_decision(
  decision   = "<与首次落账完全相同的 decision 文本>",
  outcome    = "<真实结果：时间、价格/涨跌、是否命中当初预期>",
  relation   = "caused" | "enabled" | "prevented" | "no_effect",
  task_tag   = "trade-journal.<标的或主题>.<验证期限>",
  context    = "<与首次一致的背景，补上结果发生时的环境>",
  confidence_source = "temporal"
)
```
判定口径：
- 判断 → 结果按预期发生：`caused`
- 判断创造了条件但结果另有主因：`enabled`
- 本来是这么想的，结果因此避免了损失：`prevented`
- 判断与结果无关、或结果推翻判断：`no_effect`

**第 4 步：收尾**
- 与旧记录结论相反 → 跑 `resolve_updates(limit=20, apply=false)` 先预览，把「哪条旧经验被新证据推翻」讲给用户，得到确认后再 `apply=true`。
- 明确发现自己以前记错了 → `invalidate_decision(edge_id=..., reason="...")`，并说明「保留了审计痕迹，只是不再被检索到」。

### C. 查记忆 / 复盘（用户说「我以前是不是…」「我判断对了几次」）

| 用户想问 | 调什么 |
|---|---|
| 我以前的决策和结果 | `search_causal(query=..., task_tag="trade-journal", limit=10)` |
| 不确定是事实还是决策 | `search_memory(query=...)` |
| 我的偏好/参数/持仓特征 | `search_facts(query=...)` |
| 跨任务的规律（老犯同类错） | `search_patterns(query=...)` |
| 我预测的历史命中率 | `prediction_report()` |
| 最近都记了什么 | `causal_directory(limit=20)` |
| 想要一段完整教训叙事 | `reconstruct_lesson(query=...)` |
| 这类结果通常由什么引起 | `trace_cause(outcome_description=...)` / `trace_cause_chain(...)` |

### D. 决策前用（用户说「我想…但又怕…」）

```
counterfactual_query(decision="<选项A>", alternative="<选项B>", task_tag="trade-journal", context="<当前处境>")
intervention_query(action="<准备做的事>")
```
把返回的**历史统计**如实呈现给用户，并注明这来自他自己的记录，不是对未来的预测。

## 输出格式

### 写记忆时，回复必须包含这四节

1. **【已记账】** —— 用四要素表格回显，让用户一眼确认没被理解错
   | 要素 | 内容 |
   |---|---|
   | 决策 | …… |
   | 理由 | …… |
   | 预期 | …… |
   | 验证期限 | …… |
2. **【相关历史】** —— 查到的旧记录（没有就写「暂无相关历史记录」），标明时间与当时结论
3. **【回填方式】** —— 一句话说清：「到期时你说一声『那笔结果怎么样』，我就把真实结果补进同一条记录。」并给出 `task_tag`，方便用户以后检索
4. **【待补充】** —— 还缺的要素（没有则省略此节）

### 查记忆时，回复必须包含

1. **【命中记录】** —— 逐条列：时间 / 决策 / 理由 / 当时预期 / 实际结果 / 是否验证
2. **【统计】** —— 命中率、平均验证周期、主要偏误类型（来自 `prediction_report` 与检索结果）
3. **【口径说明】** —— 明确写「以上均为历史记录统计，不构成任何建议与预期」
4. 样本不足（< 5 条）时直接说明「样本太少，统计意义有限」，不要给出百分比。

## 记忆价值

坚持用久了，这个技能会积累出四种别处拿不到的东西：

- **你自己的决策样本库**：每次记录是一条「判断 → 结果」因果边，样本越多，检索越像你自己。
- **偏误画像**：长期统计会暴露固定模式——是不是总在同一个板块追高、是不是总把「看好」当「明天就涨」、是不是验证期限定得太短。
- **可回溯的理由**：半年后你还记得当时的理由是什么，而不是只记得盈亏。
- **可复用的处境**：`context` 记多了以后，遇到相似行情，`counterfactual_query` 能调出你自己在类似处境下的真实结局——这比任何通用经验都贴身。

## 合规边界

- **只做记录与历史统计。** 输出的是「你过去是怎么做的、结果如何」，不是「你该怎么做」。
- **不给买卖建议、不给目标价、不做收益承诺、不预测涨跌。** 即使检索出的历史胜率很高，也只陈述「历史上这个模式出现过 N 次」。
- 用户问「我该买吗」→ 把问题拆成「你想记下什么判断？」并回放相关历史，不给倾向性结论。
- 回填结果时**不美化也不放大**：命中就写命中，错了就写错了，用户没说结果就不写结果。
- 事实与推测严格分开：用户说的话进 `context`，你的理解必须标注「我的理解，对吗？」再落账。

## 常见问题

1. **用户只说「记一下我买了」怎么办？**
   先把能确定的写下来（`outcome="预期：待补充"`），再一次性问齐理由和验证期限。不要因为信息不全就什么都不记——记录存在本身就是价值；也不要自己替用户编一个理由，那会污染整个记忆库。

2. **为什么首次一定要写 `relation=no_effect`、`outcome="预期：…"`？**
   因为此刻结果没发生。如果这时就写 `caused`，将来做归因和命中率统计时会把「预期」当成「事实」，整个复盘就失真了。回填时必须用**与首次完全相同的 `decision` 文本**再记一次，系统才能把两条边配成一对。

3. **一次说了好几笔 / 判断和操作混在一起怎么办？**
   一笔一条，判断与操作分开记（判断记在 `decision` 的「判断」形态里，操作记成具体成交）。同一句里的多笔交易合并成一条，会导致将来某笔回填时无法对上。

4. **用户长期不回填怎么办？**
   在每次写新记录时顺手扫一眼 `search_causal(task_tag="trade-journal")` 里的待验证项，主动提一句「你有 3 条记录还没回填，要现在补吗」。没有回填的记录，价值只有一半。
